# Data Model: Currency Conversion & Cross-Currency Transfer

**Feature**: 002-currency-fx-transfer | **Date**: 2026-06-15

This document describes the new and modified database entities for the currency conversion
and cross-currency transfer feature. All entities use PostgreSQL 16 via SQLAlchemy 2.0 async.

---

## New Entities

### FxRateSnapshot

Stores a point-in-time snapshot of all exchange rates fetched from the rate provider.
Acts as the authoritative source for rate display and transfer calculations.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `id` | UUID | PK, default uuid4 | Snapshot identifier |
| `effective_at` | TIMESTAMPTZ | NOT NULL, server_default=now() | When the rates became effective |
| `fetched_at` | TIMESTAMPTZ | NOT NULL, server_default=now() | When the snapshot was written to DB |
| `is_stale` | BOOLEAN | NOT NULL, default=False | True if provider failed to refresh |
| `provider_source` | VARCHAR(100) | NOT NULL | Identifier of the rate provider |
| `rates` | JSONB | NOT NULL | Nested map: `{from_currency: {to_currency: rate_str}}` |

**Indexes**:
- `idx_fx_rate_snapshot_effective_at DESC` — fast latest-snapshot retrieval
- `idx_fx_rate_snapshot_is_stale` — filter for non-stale snapshots

**Business rules**:
- Only one snapshot is active at a time; service always reads the most recent non-stale snapshot.
- A snapshot is marked `is_stale=True` when: (a) the provider HTTP call fails after retries,
  or (b) `now() - effective_at > FX_RATE_MAX_AGE_MINUTES`.
- Snapshots are never deleted; retained for audit and dispute resolution.
- `rates` stores decimal values as strings to preserve precision across JSON serialisation.

**State**: Stateless rows (no lifecycle transitions). Each refresh inserts a new row.

### CurrencyPair

Represents a configured, permitted pairing of source and target currencies.
Drives which pairs appear in the rate table and are selectable in the transfer form.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `id` | UUID | PK, default uuid4 | |
| `from_currency` | CHAR(3) | NOT NULL | ISO 4217 source currency code |
| `to_currency` | CHAR(3) | NOT NULL | ISO 4217 target currency code |
| `is_active` | BOOLEAN | NOT NULL, default=True | Soft-disable without deletion |
| `created_at` | TIMESTAMPTZ | NOT NULL, server_default=now() | |

**Unique constraint**: `(from_currency, to_currency)` — each direction is an independent pair.

**Indexes**:
- `idx_currency_pair_active` on `(is_active)` — filter active pairs

**Business rules**:
- A transfer can only proceed if the `(source_currency, destination_currency)` pair exists
  and `is_active = True`.
- Pairs may be seeded from the `exchange_rates.yaml` config or managed via admin operations.
- Both `EUR→USD` and `USD→EUR` must be configured as separate rows if both directions allowed.

### Notification

Stores in-app notifications generated by the system and delivered to account holders.

| Column | Type | Constraints | Notes |
|--------|------|-------------|-------|
| `id` | UUID | PK, default uuid4 | |
| `recipient_account_number` | VARCHAR(34) | NOT NULL | Account the notification belongs to |
| `transfer_id` | UUID | NOT NULL, FK → transfers.id | Associated transfer |
| `direction` | VARCHAR(10) | NOT NULL | `sent` or `received` |
| `source_amount` | NUMERIC(19,4) | NOT NULL | |
| `source_currency` | CHAR(3) | NOT NULL | |
| `net_credited_amount` | NUMERIC(19,4) | NOT NULL | Amount actually credited (after fees) |
| `net_credited_currency` | CHAR(3) | NOT NULL | |
| `read_at` | TIMESTAMPTZ | NULLABLE | NULL = unread |
| `created_at` | TIMESTAMPTZ | NOT NULL, server_default=now() | |

**Indexes**:
- `idx_notifications_recipient_read` on `(recipient_account_number, read_at)` — unread query
- `idx_notifications_transfer_id` on `transfer_id` — join to transfers

**Business rules**:
- Created atomically within the same transaction as the completed transfer.
- One row created for the sender (direction=`sent`) and one for the recipient (direction=`received`).
- `read_at` is set by the client calling `PATCH /notifications/{id}/read`.
- Notifications are append-only; never updated beyond setting `read_at`.

## Modified Entities

### Transfer (modified)

Extends the existing `transfers` table to support the full PENDING→PROCESSING→COMPLETED/FAILED
lifecycle and split fee model.

**New / changed columns**:

| Column | Type | Change | Notes |
|--------|------|--------|-------|
| `status` | VARCHAR(20) | EXTENDED | Now includes `pending`, `processing`, `completed`, `failed` |
| `sending_fee` | NUMERIC(19,4) | ADDED | Fee charged to sender on top of source amount |
| `sending_fee_currency` | CHAR(3) | ADDED | Currency of the sending fee (matches source currency) |
| `receiving_fee` | NUMERIC(19,4) | ADDED | Fee deducted from converted amount before crediting recipient |
| `receiving_fee_currency` | CHAR(3) | ADDED | Currency of the receiving fee (matches destination currency) |
| `failure_reason` | TEXT | RENAMED from `rejection_reason` | Reason for FAILED status (nullable) |
| `fx_snapshot_id` | UUID | ADDED, FK → fx_rate_snapshot.id | Rate snapshot used for this transfer |
| `rate_confirmed_at` | TIMESTAMPTZ | ADDED, NULLABLE | When customer confirmed the quoted rate |

**Status lifecycle**:

```
PENDING ──► PROCESSING ──► COMPLETED
                │
                └──────────► FAILED
```

- `PENDING`: Transfer record created; rate locked; balance reserved (pessimistic lock held during transaction).
- `PROCESSING`: Debit and credit in progress (within the same DB transaction as PENDING→PROCESSING).
- `COMPLETED`: Both debit and credit committed; notifications created; audit entry written.
- `FAILED`: At least one side could not complete; all balance changes rolled back; failure_reason set; audit entry written.

**Alembic migration**:
- `ALTER TABLE transfers ADD COLUMN sending_fee NUMERIC(19,4)` (nullable initially, then NOT NULL with default 0)
- `ALTER TABLE transfers ADD COLUMN sending_fee_currency CHAR(3)`
- `ALTER TABLE transfers ADD COLUMN receiving_fee NUMERIC(19,4)`
- `ALTER TABLE transfers ADD COLUMN receiving_fee_currency CHAR(3)`
- `ALTER TABLE transfers ADD COLUMN fx_snapshot_id UUID REFERENCES fx_rate_snapshot(id)`
- `ALTER TABLE transfers ADD COLUMN rate_confirmed_at TIMESTAMPTZ`
- `ALTER TABLE transfers RENAME COLUMN rejection_reason TO failure_reason`
- No change to existing `completed` / `rejected` rows needed; `rejected` ≡ `failed` semantically.

### AuditLogEntry (modified)

Adds new `OperationType` values to the controlled vocabulary.

**New operation_type values**:

| Value | Trigger | State-changing? |
|-------|---------|----------------|
| `fx_rate_refreshed` | Successful rate provider fetch + DB snapshot write | Yes |
| `cross_currency_transfer_initiated` | Transfer record created (PENDING) | Yes |
| `cross_currency_transfer_completed` | Transfer reaches COMPLETED | Yes |
| `cross_currency_transfer_failed` | Transfer reaches FAILED | Yes |
| `notification_delivered` | In-app notification row created | Yes |

**Audit entry detail (JSONB) for transfers**:
```json
{
  "source_amount": "100.0000",
  "source_currency": "EUR",
  "sending_fee": "2.0000",
  "destination_amount": "107.5000",
  "destination_currency": "USD",
  "receiving_fee": "1.0750",
  "net_credited": "106.4250",
  "exchange_rate": "1.07500000",
  "fx_snapshot_id": "<uuid>",
  "idempotency_key": "<key>"
}
```

## Key Validation Rules

| Rule | Enforcement Layer |
|------|-------------------|
| Source balance >= source_amount + sending_fee | Service layer (within SELECT FOR UPDATE transaction) |
| fx_snapshot_id must reference a non-stale snapshot | Service layer before transfer creation |
| Rate deviation > threshold triggers re-confirmation | Service layer (RateDeviationError → 409) |
| CurrencyPair(from, to) must exist and be active | Service layer before FX calculation |
| status transitions follow PENDING→PROCESSING→COMPLETED/FAILED only | Service layer (no direct status updates in API) |
| Notifications created in same transaction as COMPLETED status | Service layer (atomic) |
| Audit entry created in same transaction as every status change | Service layer (mandatory) |
